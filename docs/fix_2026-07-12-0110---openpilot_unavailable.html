📡 참고사항 — "publish / subscribe" 란? 프로세스 간 통신 구조

openpilot은 여러 프로세스(card, selfdrived, modeld, controlsd 등)가 동시에 독립 실행됩니다. 이 프로세스들이 서로 데이터를 주고받는 방식이 pub-sub(발행-구독)입니다.

파일 기반이 아닙니다 — 공유 메모리(shared memory) 기반

파일에 쓰고 읽으면 disk I/O 때문에 너무 느립니다. 대신 RAM의 특정 영역을 여러 프로세스가 공유합니다.

  • Publisher(발행자): 데이터를 공유 메모리의 토픽에 씀
  • Subscriber(구독자): 그 토픽을 읽음. 파일이 아닌 RAM이므로 마이크로초 단위 지연
  • 기반 기술: msgq (openpilot 자체 개발 shared memory 큐) + cereal (Cap'n Proto 직렬화)
임베디드 비유 (ATM 기준):

펌웨어 내부 인터럽트 + 링 버퍼:
  ISR(인터럽트) → 링버퍼에 데이터 write
  메인루프     → 링버퍼에서 read

openpilot (프로세스 간):
  card.py (publisher)  → msgq 공유메모리에 carParams 데이터 write
  selfdrived (subscriber) → 같은 공유메모리에서 carParams read
openpilot 주요 토픽 예시:

  토픽명           발행자       주요 구독자
  ──────────────── ──────────── ──────────────────────────
  carParams        card.py      selfdrived, controlsd
  carState         card.py      selfdrived, controlsd, ui
  modelV2          modeld       selfdrived, controlsd
  selfdriveState   selfdrived   ui, controlsd, pandad
  pandaStates      pandad       selfdrived, hardwared

→ card.py가 crash하면: carParams 토픽에 데이터가 게시되지 않음. selfdrived는 이 토픽을 기다리다가 차 인식이 안 됐다고 판단 → "openpilot unavailable" 표시.

이것이 rlog.zst 안에 carParams 메시지 타입이 없었던 이유입니다. crash 발생 시점부터 해당 토픽의 메시지가 rlog에 기록되지 않습니다.

LogReader errorLogMessage 추출
rlog 안의 에러 메시지를 daemon 별로 필터링. 
python3 -c "
for msg in LogReader(rlog):
    if msg.which() == 'errorLogMessage':
        d = json.loads(msg.errorLogMessage)
        if 'card' in d.get('ctx',{}).get('daemon',''):
            print(d.get('msg'), d.get('exc_info','')[:500])
"

3. 근본 원인

흐름

차 시동 ON
  ↓
card.py 시작 → ISO-TP 쿼리 (일부 ECU는 0x7f22 negative response → 정상)
  ↓
CAN fingerprint 성공: HYUNDAI_AZERA_HEV_6TH_GEN ✓
  ↓
car.py __init__() 에서 CP 설정 시:
  self.CP.alternativeExperience |= ALTERNATIVE_EXPERIENCE.ALWAYS_ON_LATERAL
  ↓
AttributeError: 'ALWAYS_ON_LATERAL' not found → crash
  ↓
carParams 메시지 미전송 → selfdrived가 car 인식 못함
  ↓
"openpilot unavailable" 표시

왜 제거됐나?

upstream commaai/opendbc (930eeb14)에서 panda safety 코드 재구성 시 ALWAYS_ON_LATERAL 상수가 더 이상 쓰이지 않는 것으로 판단해 제거. 우리 card.py는 FrogPilot 포팅 시 추가한 AOL 코드에서 이 상수를 참조 중이었음.

panda 펌웨어(9da8467a)는 이 비트를 실제로 체크하지 않음. 실제 AOL 동작은 pandad.cc의 heartbeat 로직으로 제어. 상수가 없으면 crash만 발생하고 기능적 영향은 없음.

4. 수정

fix abraxas4/opendbc — ALWAYS_ON_LATERAL 상수 복원

panda 펌웨어가 체크하지 않는 비트이므로, 충돌하지 않는 값(128 = 0x80)으로 복원.

class ALTERNATIVE_EXPERIENCE:

  DISABLE_STOCK_AEB = 2
