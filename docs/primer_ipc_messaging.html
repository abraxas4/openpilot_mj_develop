1. 한 줄로 보는 전체 그림

openpilot은 여러 독립 프로세스가 동시에 돌고, 서로 msgq(공유 메모리 링큐, RAM)로 메시지를 주고받습니다. 메시지 내용은 Cap’n Proto로 직렬화된 바이트입니다. 같은 메시지를 loggerd가 구독해 디스크 파일(rlog)로도 남깁니다.

핵심 구분:

  • 실시간 동작 → msgq (RAM)
  • 나중에 분석 → rlog / swaglog (디스크)
  • *.capnp 파일 → 스키마(설계도). 실시간 데이터를 파일로 공유하는 것이 아님
card ──publish carState──▶ [msgq RAM] ──subscribe──▶ controlsd controlsd ──publish carControl──▶ [msgq RAM] ──subscribe──▶ card ──CAN──▶ 차량 │ └──subscribe──▶ loggerd ──▶ rlog.zst (기록)

2. 여러 프로세스가 동시에 돈다

하나의 거대 프로그램이 아닙니다. manager가 여러 daemon을 띄웁니다. 대략 수십 개가 함께 동작합니다.

프로세스 (예)역할
manager나머지 프로세스 시작·감시
pandadpanda 보드, safety, heartbeat
card차량 fingerprint, carState, CAN 송수신
controlsd조향·가감속 제어 계산 (carControl 등)
selfdrivedengage/disengage, 이벤트·알림
modeld카메라 → 경로/차선 추론
camerad / encoderd촬영 / 영상 인코딩
loggerd / uploader로그 기록 / 업로드
ui화면

프로세스 하나가 죽으면, 그 프로세스가 publish 해야 할 토픽이 통째로 사라집니다. 예: card crash → carState 없음 → 상위 기능이 unavailable.

3. 통신과 로그는 다르다

가장 중요한 구분

로그 파일은 프로세스끼리 읽고 동작하는 통신 수단이 아닙니다. 사람이 나중에 분석하려고 남기는 기록입니다.

실시간 통신은:

  • msgq — 공유 메모리 큐 (매우 빠름, 기기 내부)
  • cereal / Cap’n Proto — 메시지 스키마와 직렬화 포맷
  • 패턴: publish / subscribe (발행–구독)
통신 (실시간)로그 (기록)
목적 지금 차를 제어 나중에 원인 분석·업로드
매체 RAM (msgq) 디스크 파일
실패 시 제어에 직접 영향 분석만 어려워짐 (이상적으로 제어와 분리)
서로 참조? 토픽으로 구독 로그끼리 통신하지 않음

4. msgq = RAM 위의 메시지 큐

4.1 공유 메모리란?

네, RAM입니다. 디스크(SSD/eMMC에 오래 쓰는 파일)가 아닙니다. 여러 프로세스가 같은 물리 메모리 페이지를 각자의 가상 주소 공간에 매핑(mmap)해서 한쪽이 쓴 바이트를 다른 쪽이 곧바로 읽을 수 있습니다.

/dev/shm 은 뭔가?

Linux에서 msgq는 대략 이런 경로를 씁니다:

/dev/shm/msgq_carControl
/dev/shm/msgq_carState
…

/dev/shm은 파일처럼 보이지만 tmpfs입니다. 이름·권한은 파일 API로 다루고, 내용은 메모리(RAM)에 있습니다. 전원 끄면 사라집니다. “파일을 통해 디스크에 실시간 데이터를 실어 나른다”가 아닙니다.

4.2 전역 구조체 하나? → 아니다. 토픽별 링큐

모든 프로세스가 거대한 공유 구조체를 같이 쓰는 방식이 아닙니다. 토픽(이름)마다 별도의 링 버퍼가 있습니다.

[ RAM / msgq ] carState 큐 ← card 가 publish (관례 ~100Hz) carControl 큐 ← controlsd 가 publish modelV2 큐 ← modeld 가 publish (관례 ~20Hz) pandaStates …
  • 발행자(publisher)는 자기 토픽 큐에 메시지를 넣음
  • 구독자(subscriber)는 필요한 토픽만 구독
  • 토픽당 writer 1명, reader는 여러 명 가능 (SPMC)

4.3 링 버퍼 레이아웃 (구현 관점)

토픽 하나당 대략:

┌─────────── header (메타) ───────────┐ │ reader 수, write pointer, write uid │ │ reader별 read pointer / valid 플래그 │ └──────────────────────────────────────┘ ┌─────────── data (링) ───────────────┐ │ [size 8B][payload…][size][payload…] │ │ size == -1 이면 wrap (처음으로) │ └──────────────────────────────────────┘
  • 쓰기는 write pointer를 전진
  • 읽기는 자기 read pointer에서 size를 보고 payload를 복사(copy)한 뒤 전진
  • 느린 reader가 너무 뒤처지면 valid가 깨지고, 최신 위치로 reset (중간 메시지 drop)
  • 제어용 구독은 보통 conflate (쌓인 것 중 최신 1개만 사용)

큐 크기는 서비스 정의에 따라 다릅니다. 예: 일반 토픽 약 250KB, CAN/큰 메시지 수 MB 단위 (openpilot/cereal/services.py의 QueueSize).

4.4 “정해진 주소에 필드를 쓰나?”

약속내용
토픽 이름"carControl" → /dev/shm/msgq_carControl
페이로드 포맷Cap’n Proto log.Event 바이트
대략 주기services.py의 frequency (관례 + alive 검사)
고정 필드 오프셋 공유없음 — 링 안에서 포인터가 움직임

5. Cap’n Proto는 무엇인가

Cap’n Proto(줄여 capnp)는 데이터를 어떤 바이트 모양으로 표현할지 정하는 스키마 + 직렬화 시스템입니다.

것역할실시간 데이터?
log.capnp, car.capnp 등 메시지 설계도 (필드 이름·타입) 아니오 — 정의 파일
Event.to_bytes() 구조체 → 바이트 직렬화 그 바이트가 msgq/rlog로 감
Event.from_bytes() 바이트 → 구조체로 읽기 구독 직후 사용
오해 금지

“capnp 파일로 실시간 데이터를 공유한다”가 아닙니다.

실시간 경로: Cap’n Proto 바이트 → msgq(RAM)
기록 경로: 같은 종류의 바이트 → rlog 파일

“Zero-copy”는 보통 “디스크 없이 메모리 버퍼 위에서 필드를 읽는다”는 뜻에 가깝고, 프로세스 간 객체를 포인터로 직접 공유한다는 뜻이 아닙니다. msgq 수신 시 링에서 유저 버퍼로 copy 1회가 있습니다.

openpilot에서 대부분의 토픽은 공통 봉투 log.Event 를 씁니다. 그 안에 union으로 carState, carControl, modelV2 … 가 들어갑니다. 구독 후 msg.which() 로 “지금 이 메시지가 어떤 서비스인지”를 알 수 있습니다.

6. 바닥까지 레이어 스택

[앱] controlsd / card / loggerd … │ cereal API: new_message, PubMaster, SubMaster ▼ [cereal] log.Event (Cap’n Proto) │ to_bytes() / from_bytes() ▼ [msgq API] PubSocket.send / SubSocket.receive │ ▼ [msgq 구현] open(/dev/shm/msgq_<topic>) + mmap(MAP_SHARED) 링 버퍼 write/read pointer (lock-free SPMC) │ ▼ [커널] tmpfs 페이지 = 물리 RAM

관련 코드 위치 (학습용):

  • openpilot/cereal/messaging/__init__.py — PubMaster, SubMaster, new_message
  • openpilot/cereal/services.py — 토픽 목록, 주기, 큐 크기, 로그 여부
  • msgq_repo/msgq/msgq.cc, msgq.h — 공유 메모리 링큐 본체
  • msgq_repo/README.md — write/read/reset 알고리즘 설명

참고: 카메라 프레임 같은 매우 큰 연속 버퍼는 일반 msgq와 별도로 VisionIPC 경로를 씁니다. 개념(공유 메모리)은 비슷하고, 용도가 영상 쪽에 특화되어 있습니다.

7. 생성측 / 구독측 예제

7.1 생성 (publisher) — controlsd 가 carControl 을 보낼 때

실제 코드 흐름과 동일한 패턴:

# 1) 소켓 준비 (프로세스 시작 시 한 번)
pm = messaging.PubMaster(['carControl', 'controlsState'])

# 2) 매 주기(예: 100Hz) 메시지 조립
msg = messaging.new_message('carControl')   # log.Event + carControl 슬롯
msg.valid = True
msg.carControl.enabled = True
msg.carControl.latActive = True
msg.carControl.actuators.torque = 0.2

# 3) 전송
pm.send('carControl', msg)

PubMaster.send 내부에서 하는 일:

  1. 이미 bytes가 아니면 dat.to_bytes() — Cap’n Proto 직렬화
  2. PubSocket.send(bytes) — msgq 링에 size + payload 기록
controlsd 프로세스 힙 Event builder ──to_bytes()──▶ [바이트 배열] │ ▼ memcpy into ring /dev/shm/msgq_carControl (RAM)

7.2 구독 (subscriber) — card 가 carControl 을 받을 때

# 1) 구독 준비
sm = messaging.SubMaster(['carControl', 'pandaStates', ...])

# 2) 루프마다 최신 메시지 흡수
sm.update(timeout_ms)     # poll + receive + from_bytes

# 3) 필드 사용
if sm.updated['carControl']:
    cc = sm['carControl']           # 이미 파싱된 구조체
    lat = cc.latActive
    torque = cc.actuators.torque

SubMaster가 하는 일:

  1. 토픽마다 sub_sock 연결 (제어용은 보통 conflate=True)
  2. receive()로 링에서 바이트 복사
  3. log.Event.from_bytes(...)로 파싱
  4. self.data['carControl'] = msg.carControl 저장
  5. 주기·지연을 보고 alive / freq_ok / valid 갱신

7.3 최소 완전체 (두 프로세스 상상)

# === 프로세스 A: publisher ===
from openpilot.cereal import messaging

pm = messaging.PubMaster(['carControl'])
msg = messaging.new_message('carControl')
msg.valid = True
msg.carControl.latActive = True
msg.carControl.actuators.torque = 0.2
pm.send('carControl', msg)

# === 프로세스 B: subscriber ===
from openpilot.cereal import messaging

sm = messaging.SubMaster(['carControl'])
sm.update(1000)
if sm.updated['carControl']:
    print(sm['carControl'].latActive, sm['carControl'].actuators.torque)

같은 기기에서 A와 B가 돌면, B는 A가 넣은 RAM 링의 복사본을 읽습니다. 객체 포인터를 공유하는 것이 아니라 직렬화된 바이트를 공유합니다.

8. 로그 파일은 어디에, 어떻게 남나

8.1 종류

위치파일내용
/data/media/0/realdata/<route>--<seg>/ rlog.zst cereal 메시지 압축 기록 (분석 1순위)
같은 폴더 qlog.zst rlog 축약본 (업로드용, decimation)
같은 폴더 fcamera.hevc 등 카메라 영상 (별도 파이프라인)
/data/log/swaglog.* swaglog 프로세스 디버그 텍스트/JSON (crash traceback 등)

세그먼트 --0, --1 … 은 대략 1분 단위 조각입니다.

8.2 실시간과 같은 속도로 디스크에 쓰나?

제어 경로와 로그 경로는 분리되어 있습니다.

controlsd ──▶ msgq(RAM) ──▶ card ← 실시간 (필수) │ └──▶ loggerd ──버퍼/압축──▶ 디스크 ← 부가 (기록)
  • 제어는 디스크 fsync를 기다리지 않도록 설계
  • loggerd는 메시지를 받아 메모리 버퍼에 모은 뒤 압축·블록 단위로 write
  • 토픽마다 주기가 다름 (100Hz, 20Hz, 10Hz …). “전 시스템을 1ms마다 덤프”가 아님
  • should_log, qlog decimation으로 파일 쪽만 솎기도 함
  • 디스크가 못 따라가면 로그 품질이 깨질 수 있으나, 이상적으로 제어 루프와 분리

swaglog는 cereal 토픽 스트림과 별도로, 각 프로세스가 남기는 개발자용 텍스트 로그에 가깝습니다. rlog와 역할이 다릅니다.

9. 기억할 체크리스트

  1. openpilot = 다중 프로세스 + 토픽 기반 pub/sub
  2. 통신 = msgq (RAM), 로그 = 디스크 기록 (로그로 통신하지 않음)
  3. 공유 메모리 = 물리 RAM 매핑. /dev/shm은 tmpfs(파일 API + RAM 내용)
  4. 토픽마다 링큐. 전역 공유 구조체 하나 아님
  5. Cap’n Proto = 스키마 + 바이트 포맷. *.capnp 파일 자체가 실시간 통로 아님
  6. publish: 구조체 → to_bytes() → 링에 기록 / subscribe: 링에서 복사 → from_bytes()
  7. 느린 구독자는 drop·reset 가능. 제어는 보통 conflate(최신값)
  8. loggerd도 같은 바이트를 구독해 파일로 미러링. 버퍼·압축·(qlog) 샘플 축소
