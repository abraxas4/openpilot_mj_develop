④ “세 칸”은 뭔가? 로그는 어떻게 쌓이나? (중요 Q&A)

먼저 답

예, 표 위쪽 3행이 그 “세 칸”입니다.

① carControl.latActive (true/false)

② pandaStates.controlsAllowed (true/false)

③ pandaStates.safetyTxBlocked (숫자, 누적 카운터)

다만 이 세 칸은 rlog 파일 안에 미리 “표 3열”로 그려져 있는 것이 아닙니다. 우리가 나중에 LogReader로 메시지를 읽으면서 머릿속/스크립트로 나란히 비교한 뷰입니다.

Q1. 세 칸 = 표 위 3개?
맞습니다.
표의 1~3행 (latActive / controlsAllowed / safetyTxBlocked).
4행 harness, 5행 AOL은 “혹시 케이블/플래그 문제인가?”를 같이 본 보조 항목입니다.
Q2. 값이 바뀔 때만 쓰나?
아니요. “변화 있을 때만”이 아닙니다.
각 프로세스가 주기적으로 메시지 통째로 보냅니다.
예: controlsd 는 약 100Hz (초당 ~100번) 로 carControl 전체(그 안의 latActive 포함)를 publish 합니다.
값이 true→true 로 같아도, 그 시점의 스냅샷이 또 한 번 나갑니다.
panda 쪽 pandaStates 도 주기적으로 상태 묶음을 올립니다. (controlsAllowed, safetyTxBlocked 가 그 묶음 안의 필드)
Q3. 고정 너비로 칸을 채우나?
아니요. 텍스트 CSV처럼 “칸 너비를 맞춰 채우는” 방식이 아닙니다.
형식은 Cap’n Proto(cereal) 이진 메시지입니다.
메시지 하나 = “이 시각의 carControl 전체” 또는 “이 시각의 pandaStates 전체”.
true/false 는 bool 필드, safetyTxBlocked 는 정수 필드입니다.
사람이 읽는 “표 3칸”은 나중에 우리가 뽑아 만든 것이고, 파일 원본은 이진 스트림(+ zstd 압축 = rlog.zst) 입니다.
Q4. 파일을 계속 write? 통신?
둘 다인데, 순서가 있습니다.
1순위 = 통신(msgq): controlsd / pandad 등이 실시간으로 publish.
다른 프로세스(card, ui …)가 subscribe 해서 동작합니다.
2순위 = 기록(loggerd): loggerd 가 같은 메시지들을 구독해서 디스크에 이어 씁니다 → 주행 중 rlog.zst 가 계속 커집니다.
즉 “분석용 로그 전용으로만 쓰는” 게 아니라, 이미 통신으로 오가는 내용을 옆에서 녹음하는 구조입니다.

실제

이진 cereal 메시지 (텍스트 표 아님)

이건 true/false가 아니라 누적 카운터에 가깝습니다. “지금까지 안전 규칙 때문에 막힌 송신 횟수”가 메시지마다 실려 나옵니다.

그래서 우리는 “true/false 토글”이 아니라 min=0, max=수천 처럼 구간 안에서 숫자가 불어났는지를 봤습니다. 불어나면 = 그 주행 동안 차단이 계속 일어났다.

정리 한 줄

세 칸 = 우리가 비교하려고 고른 세 필드이지, 로그 파일의 고정 포맷 열이 아닙니다. 코드는 변화 시에만 쓰는 게 아니라 주기로 메시지 전체를 통신하고, loggerd가 그걸 파일에 계속 이어 씁니다.

다시 한 번 — “로그를 연다”의 실체

1) SSH로 3X 접속

2) ls 로 최신 /data/media/0/realdata/…/rlog.zst 경로 확인

3) LogReader(rlog경로) 로 메시지 순회

4) latActive / controlsAllowed / safetyTxBlocked 집계

5) true인데 false + 차단 증가 → safety 문제라고 결론

전체 복붙 명령은 §9 따라하기 STEP 2 → STEP 6 에 있습니다.

[ 시간 순서 ] 어제 (정상) ─────────── AOL ON → 조향 명령 생성 → panda가 허용 → 차가 따라감 ✓ 머지 직후 (1단계 버그) ───────────────────── card 프로세스 사망(AttributeError) → carState 없음 → 화면 "unavailable" ✗ Python 상수만 복구 후 (2단계 버그 = 본 문제) ─────────────────────────────────────────── AOL ON → 조향 명령 생성 → panda가 전부 차단 → 풀리는 느낌 ✗ (C safety 로직 유실) 수정 후 ────── AOL ON → 조향 명령 생성 → panda가 허용 → 정상 ✓

위 그림에서 기억할 것은 하나뿐입니다. “소프트웨어가 조향을 시도한다”와 “실제로 차에 신호가 나간다”는 다른 단계입니다. 이번 버그는 두 번째 단계(panda 문지기)가 막힌 것이었습니다.

2. 처음 나오는 단어 전부 설명

아래 단어를 모르면 본문이 한 줄마다 끊깁니다. 처음 읽기 전에 한 번 훑어보고, 본문에서 다시 나오면 여기로 돌아오면 됩니다.

openpilot
comma.ai가 만든 오픈소스 자율주행/ADAS 소프트웨어. 카메라·센서 정보를 보고 조향·가감속 명령을 계산합니다. 예: 차선 따라가기, 크루즈, (커스텀) AOL 등
comma 3X / tizi
openpilot을 돌리는 기기(작은 컴퓨터). 3X는 제품 이름, tizi는 내부 코드명에 가깝습니다. 예: 차 앞유리에 붙인 그 장치
upstream
“공식 원본 저장소”. 여기서는 commaai/openpilot. 우리가 포크(복사본)를 쓰고, 가끔 공식 변경을 가져와 합칩니다. 예: 회사 본점 코드 ↔ 우리가 고쳐 쓰는 지점 코드
fork / origin
fork = 내 GitHub 계정에 복사해 둔 저장소. origin = 내 컴퓨터 git이 “기본 원격”으로 부르는 그 주소 (보통 내 fork). 이 프로젝트: origin = abraxas4/openpilot_mj_develop
merge (머지)
다른 브랜치/저장소의 코드를 내 브랜치에 합치는 작업. 합치다 보면 우리가 따로 넣어 둔 코드가 덮이거나 빠질 수 있습니다. 이번 사건: upstream merge 후 AOL safety가 빠짐
브랜치 (branch)
코드 역사의 “갈래 이름”. 같은 저장소 안에서도 실험용/배포용을 나눕니다. 우리가 쓰는 것: openpilot의 frogpilot_port
서브모듈 (submodule)
“다른 git 저장소를 폴더처럼 끼워 넣는” 방식. openpilot 안에 opendbc가 서브모듈로 들어 있습니다. 부모(openpilot)는 “opendbc의 어느 커밋을 쓸지” 해시로 고정합니다. 폴더 이름은 보통 opendbc_repo
opendbc
차량 CAN 메시지 정의 + safety(안전) 규칙이 있는 저장소. “이 차는 어떤 패킷을 쓰나”, “어떤 상황에서 조향 TX를 허용하나”가 여기 있습니다. 이번 수정의 핵심 장소
panda
차와 통신하는 작은 보드(USB로 연결). CAN을 주고받고, 위험한 명령이 나가지 않게 safety 검사를 합니다. safety 소스 코드는 opendbc 쪽에 있고, 빌드 때 panda 펌웨어에 들어갑니다. 비유: 조향 명령의 최종 문지기
CAN
자동차 전장 부품끼리 쓰는 통신 버스. openpilot의 조향/가속 명령도 결국 CAN 패킷으로 차에 전달됩니다. 비유: 차 안의 공용 전깃줄 + 약속된 메시지 형식
하네스 (harness)
3X/panda를 차 OBD·전장에 연결하는 케이블/커넥터 세트. 연결 상태는 로그에 harnessStatus 로 남습니다. normal = 정상 연결, notConnected = 미연결(시동 꺼진 책상 위에서도 흔함)
AOL / Always On Lateral
크루즈(ACC)를 안 켜도 횡방향(조향)만 계속 잡는 커스텀 기능. stock(공식 기본) openpilot은 보통 크루즈 engage 될 때만 조향을 허용합니다. AOL은 그 제한을 풀어 주는 쪽에 가깝습니다. 증상 표현: “잡았다가 풀린다”
engage / disengage
engage = openpilot 제어를 켬. disengage = 끔/풀림. UI 버튼·크루즈 버튼·안전 이벤트 등으로 상태가 바뀝니다.
unavailable (“openpilot unavailable”)
UI가 “지금 제어할 준비가 안 됐다”고 보여주는 상태. 카메라 화면은 보여도 engage가 안 될 수 있습니다. 흔한 원인: 필수 프로세스가 죽었거나, 필수 데이터가 안 옴. 이번 1단계: card 프로세스가 crash해서 carState가 없음
프로세스 / 데몬 (daemon)
동시에 돌아가는 프로그램 조각. openpilot은 하나의 거대 프로그램이 아니라, manager가 여러 데몬을 띄웁니다. card, controlsd, pandad, ui …
manager
나머지 데몬을 시작·감시하는 총괄 프로세스.
card
차량 쪽 담당. fingerprint(차종 인식), carState 생성, CAN 송수신 루프. 죽으면 차 상태가 안 나와 unavailable이 잘 납니다.
controlsd
조향/가감속 제어값을 계산하는 프로세스. “핸들을 얼마나 돌릴지” 같은 숫자를 만듭니다. 만들어도, panda가 막으면 차에 안 갑니다.
selfdrived
engage/disengage 상태, 이벤트/알림을 다루는 쪽에 가깝습니다.
modeld / camerad / loggerd
modeld: 카메라 영상으로 차선·경로 추론. camerad: 카메라 촬영. loggerd: 통신 내용을 파일로 기록.
msgq
기기 안에서 프로세스끼리 데이터를 주고받는 빠른 공유 메모리 큐. 실시간 동작에 쓰입니다. 로그 파일이 아닙니다.
cereal / Cap'n Proto
메시지 형식(스키마) 정의. “carState 안에는 어떤 필드가 있나” 같은 약속. 프로세스들은 이 형식으로 publish/subscribe 합니다.
publish / subscribe (발행-구독)
누가 데이터를 뿌리고(publish), 누가 받아 보는지(subscribe). 서로 직접 함수 호출하지 않고, 토픽 이름으로 연결됩니다. card가 carState를 publish → controlsd가 subscribe
토픽 (topic)
메시지 종류 이름. carState, carControl, pandaStates, modelV2 …
rlog / rlog.zst
주행 중 cereal 메시지를 시간순으로 담은 압축 로그. 문제 분석 1순위 파일입니다. 위치는 대략 /data/media/0/realdata/<route>--<seg>/rlog.zst
swaglog
프로세스들이 남기는 텍스트/JSON 디버그 로그. crash traceback, WARNING을 빠르게 찾을 때 씁니다. 위치: /data/log/swaglog.*
route / segment
route = 한 번 주행 기록의 큰 묶음 이름. segment = 그 안의 약 1분 단위 조각 (--0, --1 …). 000001dd--2bace7efd3--0
LogReader
rlog를 파이썬에서 읽어 메시지별로 순회하는 도구. “이 주행에서 controlsAllowed가 몇 번 true였나?”를 셀 때 씁니다.
fingerprint
“이 차가 어떤 차종 설정인지” 인식한 결과. HYUNDAI_AZERA_HEV_6TH_GEN
carState / carParams / carControl
carParams: 차종·옵션 등 (시작 시 한번 크게 잡힘). carState: 지금 차 상태 (속도, 페달, 크루즈 상태 등) 실시간. carControl: openpilot이 내보내는 제어 명령 (조향 활성 등).
latActive
횡방향(lateral) 제어가 활성인지. controlsd 쪽 “조향 중” 신호에 가깝습니다. true여도 panda가 막으면 차는 안 따라갑니다.
controlsAllowed
panda safety가 “지금 제어 명령을 내보내도 된다”고 허용했는지. 이번 버그의 핵심 지표. 버그 시 주행 중 항상 false.
safety / safetyTxBlocked
safety = “위험한 CAN 송신을 막는 규칙”. safetyTxBlocked = 막힌 송신 횟수 누적. 숫자가 계속 늘면 “명령은 있는데 문지기가 계속 거절” 중이라는 뜻.
alternativeExperience
실험/대안 경험 플래그 비트 묶음. AOL 같은 옵션이 여기 비트로 표현됩니다. Python 숫자와 C 매크로 비트가 같아야 합니다.
AttributeError
파이썬에서 “없는 속성/상수를 읽었다”는 오류. 이번 1단계: ALWAYS_ON_LATERAL 상수가 사라져 card가 죽음.
C safety / Python 상수
Python 상수: 상위 소프트웨어가 “AOL 켠다”고 표시하는 스위치. C safety: panda에 들어가는 실제 허용/차단 로직. 스위치만 있고 로직이 없으면 UI/플래그는 on인데 조향은 막힙니다.
SSH
PC에서 3X 셸에 원격 접속하는 방법. 로그 확인·명령 실행에 사용합니다. 같은 Wi‑Fi 필요.
비유로 한 번에 붙이기

식당 주방으로 비유하면:

  • controlsd = 요리사 (조향 레시피/명령을 만든다)
  • msgq/cereal = 주방전표 전달 시스템
  • card = 창구 (전표를 받아 CAN으로 내보냄)
  • panda safety = 최종 검사원 (위험한 주문은 반려)
  • loggerd / rlog = CCTV 녹화 (나중에 왜 음식이 안 나갔는지 볼 때)

이번 사고: 요리사는 계속 요리했는데(latActive=true), 검사원이 전부 반려(controlsAllowed=false, safetyTxBlocked 증가)한 상황.

3. 화면에 보인 증상

증상 A 머지 직후 일부 구간에서 "openpilot unavailable". GUI/카메라는 보이지만 engage 불가.

증상 B (본 문제) 주행 중 AOL이 잡았다가 자꾸 풀리는 느낌. 어제(upstream merge 전)까지는 정상. 차량/하네스 변경 없음.

배경 브랜치 frogpilot_port 에 commaai/openpilot 을 merge (2026-07-11). Python 패키지 구조가 루트 → openpilot/ 아래로 이동하는 큰 머지. opendbc는 별도 fork(abraxas4/opendbc)를 서브모듈로 사용.

증상 A — unavailable

필수 프로세스/데이터가 없음.

예: card가 죽으면 carState가 안 나옴.

→ UI가 “준비 안 됨”.

증상 B — 풀리는 느낌

프로세스는 살아 있음.

조향 계산도 함.

→ 그런데 panda가 TX를 막음.

두 증상은 같은 머지에서 연쇄로 나왔지만, 원인은 다릅니다. 먼저 A를 고친 뒤에도 B가 남아 있어서, B를 따로 추적했습니다.

4. openpilot을 그림으로 이해하기

4.1 한 대의 컴퓨터, 여러 개의 프로그램

openpilot은 “하나의 큰 실행 파일”이 아닙니다. manager가 여러 데몬을 동시에 띄웁니다. 대략 수십 개입니다.

┌─────────────┐ │ manager │ 총괄: 시작/감시 └──────┬──────┘ ┌───────────────┼────────────────┐ ▼ ▼ ▼ ┌────────┐ ┌──────────┐ ┌──────────┐ │ camerad│ │ modeld │ │ ui │ │ 촬영 │ │ 차선추론 │ │ 화면 │ └───┬────┘ └────┬─────┘ └──────────┘ │ │ ▼ ▼ ┌────────────────────────┐ │ controlsd │ 조향/가감속 계산 └───────────┬────────────┘ │ carControl ▼ ┌────────────────────────┐ │ card │ 차 상태 + CAN └───────────┬────────────┘ │ ▼ ┌────────────────────────┐ │ pandad + panda 보드 │ 문지기(safety) + CAN └───────────┬────────────┘ ▼ 차량 ECU
프로세스쉬운 역할죽으면?
manager나머지 시작/감시전체 난리
pandadpanda와 대화, safety/heartbeat차 통신 이상
card차종 인식, carState, CAN 루프unavailable 흔함
controlsd조향/가감속 숫자 계산제어 안 됨
selfdrivedengage 상태·이벤트상태/알림 이상
modeld카메라 → 경로차로 못 봄
loggerd기록당장 달릴 순 있어도 원인 추적 불가
ui화면표시만 문제일 수도
초보자가 기억할 것 2줄

1) 프로세스가 죽으면 그 프로세스가 만들어야 할 데이터가 통째로 사라집니다.

2) 프로세스가 살아 있어도 panda safety가 막으면 차는 안 움직입니다.

4.2 “조향이 실제로 나가려면” 체크리스트

1. AOL/engage 의도 ON
→
2. controlsd가 latActive=true
→
3. card가 CAN 송신 시도
→
4. panda controlsAllowed=true
→
5. 차가 조향

이번 버그는 1~3은 OK, 4에서 실패였습니다.

정상: [의도 ON] → [latActive true] → [CAN 송신] → [controlsAllowed true] → 차 움직임 ✓ 이번 버그(2단계): [의도 ON] → [latActive true] → [CAN 송신 시도] → [controlsAllowed false] ✗ │ └→ safetyTxBlocked 숫자만 계속 증가

5. 로그란 무엇인가 (통신이 아님)

가장 헷갈리는 부분

로그 파일끼리 서로 대화하지 않습니다.

로그는 CCTV입니다. 실시간으로 차가 움직이는 데 쓰이는 통로가 아닙니다.

실시간 통로는 msgq + cereal (publish/subscribe) 입니다.

loggerd는 그 통로 위의 메시지를 옆으로 복사해 파일에 남깁니다.

실시간 (동작에 사용): card --publish carState--> [msgq] --subscribe--> controlsd controlsd --publish carControl--> [msgq] --subscribe--> card → panda → 차량 기록 (나중에 사람이 분석): 같은 토픽을 loggerd가 구독 → rlog.zst 파일에 저장 각 프로세스가 따로 남기는 텍스트 → swaglog 분석: rlog.zst / swaglog → LogReader / strings / grep → 사람
위치 종류 뭐가 들어 있나 언제 보나
/data/media/0/realdata/<route>--<seg>/ rlog.zst carState, pandaStates, carControl, errorLogMessage 등 거의 전부 압축 이진 문제 분석 1순위
같은 폴더 qlog.zst rlog 축약본 (업로드용) 용량 줄인 사본
같은 폴더 fcamera.hevc 등 카메라 영상 화면으로 확인
/data/log/swaglog.* swaglog crash traceback, WARNING 텍스트 빠른 1차 검색
예: 무엇을 어느 로그에서 보나
  • “card가 AttributeError로 죽었나?” → swaglog 또는 rlog의 errorLogMessage
  • “controlsAllowed가 계속 false였나?” → rlog의 pandaStates
  • “latActive는 true였나?” → rlog의 carControl
  • “하네스가 normal이었나?” → rlog의 pandaStates.harnessStatus

세그먼트 이름 예: 000001dd--2bace7efd3--0. 끝의 --0, --1 … 은 약 1분 단위 조각입니다.

6. 처음에 잘못 생각한 것 (하네스)

오판 → 정정

조사 초반, 기기가 차 밖 / 시동 꺼짐 / USB만 연결 상태일 때 harnessStatus=notConnected, 전압 약 4.8V 를 보고 “OBD 하네스 미연결이 원인”이라고 단정한 적이 있습니다.

그건 그 순간 책상 위 상태를 설명할 뿐입니다. “어제까지 되던 차가 머지 후 풀린다”는 본 문제의 원인이 아닙니다.

  • 실제 주행 세그먼트(000001dd): harness=normal, 전압 ~14V
  • 사용자: 하네스 변경 없음
  • 진짜 원인: 소프트웨어 (AOL C safety 유실)
[ 잘못된 연결 ] 책상 위 측정값 ──X──▶ “케이블 문제!” (성급한 결론) │ │ (시동 OFF면 notConnected / 4.8V 가 흔함) ▼ 주행 rlog를 보면 harness normal → 하드웨어 가설 탈락 │ ▼ 소프트웨어 플래그 vs panda 허용 여부 비교 → 원인 발견

7. 진짜 원인 2단계 (가장 중요)

한 번에 두 가지가 겹쳤습니다. 먼저 프로세스가 죽었고(1단계), 그걸 고친 뒤에도 문지기 규칙이 비어 있었습니다(2단계).

1단계 — card.py crash → unavailable

upstream opendbc가 Python 상수 ALTERNATIVE_EXPERIENCE.ALWAYS_ON_LATERAL 을 제거했습니다.

card.py 는 fingerprint 직후 그 상수를 읽습니다.

상수가 없으니 AttributeError → card 프로세스 crash.

card가 죽으면 carParams/carState 가 publish되지 않습니다.

UI는 unavailable을 보여 줍니다.

1차 대응: Python 상수만 복구 → crash 방지 → GUI 회복.

하지만 이것만으로는 AOL “풀림”이 해결되지 않았습니다.

2단계 — AOL C safety 유실 → “풀리는 느낌” (본 원인)

Python 쪽 “AOL 켠다” 표시는 다시 살아났습니다.

그런데 panda가 실제로 쓰는 C safety 로직이 opendbc rebase/머지 과정에서 빠졌습니다.

예전에 있던 커밋 (opendbc 옛 브랜치 frogpilot_port):

  • 5945563a Add Hyundai always-on lateral safety support
  • 5fd02d0d Relax Hyundai AOL safety on brake and regen

이 내용이 hyundai_common.h / safety.h 에서 사라졌습니다.

결과: stock 규칙대로, 크루즈 engage 없이는 controls_allowed 가 true가 되지 않음 → AOL만 켠 상태에서는 조향 CAN이 전부 차단.

주행 rlog로 증명된 사실 (세그먼트 000001dd)
항목값쉬운 해석
harness / voltagenormal / ~14V하드웨어 연결 OK
fingerprintHYUNDAI_AZERA_HEV_6TH_GEN차종 인식 OK
alternativeExperience129 (당시 Python bit 128+1)소프트웨어 AOL 쪽 플래그 ON

→ openpilot은 조향 명령을 만들고, panda safety가 막아서 차가 안 따라감 → “풀림”.

한 줄 요약

AOL은 “크루즈 없이 횡방향만 켠다”는 기능입니다. stock safety는 원래 크루즈 engage 될 때만 controls_allowed=true 로 둡니다. 우리가 넣었던 C 예외 로직이 머지로 빠지면서, AOL이 소프트웨어상 on이어도 panda가 조향 패킷을 전부 차단한 것이 원인입니다.

문 비유 (2단계만)

Python 상수 = 문에 “영업 중” 팻말 다시 붙임.

C safety = 문 자물쇠를 열어 주는 실제 열쇠 로직.

팻말만 있고 자물쇠 로직이 없으면, 손님(조향 명령)은 계속 오는데 문은 안 열립니다.

버그 상태

Python: AOL 플래그 있음

C: AOL이면 허용 분기 없음

latActive true + controlsAllowed false

TxBlocked 폭주

정상 AOL

Python 비트와 C 매크로 일치

C: AOL이면 cruise 없이도 allowed

controlsAllowed에 true 존재

TxBlocked 폭주 없음

코드에서 한 일 (순서대로)

  1. opendbc/safety/__init__.py — ALWAYS_ON_LATERAL = 32 (C 매크로와 비트 일치. 임시로 쓰던 128 폐기)
  2. opendbc/safety/declarations.h — #define ALT_EXP_ALWAYS_ON_LATERAL 32
  3. opendbc/safety/modes/hyundai_common.h — AOL이면 cruise 없이도 controls_allowed = true
  4. opendbc/safety/safety.h — AOL이면 brake/regen rising edge로 controls 끄지 않음
  5. 테스트 복구: TestHyundaiSafetyAlwaysOnLateral
  6. openpilot 서브모듈 포인터를 위 opendbc 커밋으로 갱신 후 push 
// hyundai_common.h 핵심 아이디어 (의사코드)
if (hyundai_always_on_lateral()) {
  controls_allowed = true;   // 크루즈 없어도 허용
  return;
}
// 그 외: 기존처럼 cruise engage 될 때만 true
왜 panda 저장소를 따로 fork하지 않았나

panda 펌웨어는 #include "opendbc/safety/safety.h" 로 opendbc 안의 safety 코드를 그대로 컴파일합니다.

그래서 AOL 로직은 opendbc만 고치면 됩니다. 기기에서 재빌드/재부팅 시 새 safety가 panda에 올라갑니다.

수정 위치 한눈에: openpilot (부모 저장소) └── opendbc_repo/ ← 서브모듈 (abraxas4/opendbc) └── opendbc/safety/ ├── __init__.py ← Python 비트 32 ├── declarations.h ← C 매크로 32 ├── modes/hyundai_common.h ← AOL이면 allowed └── safety.h ← brake/regen 예외 panda 펌웨어 빌드 시 위 safety.h 를 포함 → 별도 panda fork 불필요

from openpilot.tools.lib.logreader import LogReader
from collections import Counter
RLOG = '/data/media/0/realdata/최신세그먼트/rlog.zst'

ctrl = Counter(); alt = Counter(); harness = Counter()
lat = Counter(); txb = []; aol = Counter()
cp = None
for msg in LogReader(RLOG):
    w = msg.which()
    if w == 'carParams' and cp is None:
        cp = msg.carParams
        print('fingerprint', cp.carFingerprint)
        print('alternativeExperience', cp.alternativeExperience)
        print('long', cp.openpilotLongitudinalControl)
    elif w == 'pandaStates':
        for p in msg.pandaStates:
            ctrl[bool(p.controlsAllowed)] += 1
            alt[int(p.alternativeExperience)] += 1
            harness[str(p.harnessStatus)] += 1
            txb.append(p.safetyTxBlocked)
    elif w == 'carControl':
        lat[bool(msg.carControl.latActive)] += 1
    elif w == 'frogpilotCarState':
        aol[bool(msg.frogpilotCarState.alwaysOnLateralEnabled)] += 1

print('harness', dict(harness))
print('controlsAllowed', dict(ctrl))
print('altExperience', dict(alt))
print('latActive', dict(lat))
print('AOL enabled', dict(aol))
if txb:
    print('safetyTxBlocked min/max', min(txb), max(txb))

12. 다음에 같은 일이 나면

  1. 머지 후 커스텀 safety/AOL 은 Python 상수뿐 아니라 C safety + 테스트까지 살아 있는지 확인.
  2. unavailable 이면 먼저 card/selfdrived crash (swaglog + errorLogMessage).
  3. 풀림 / 조향 안 됨 이면 latActive 와 controlsAllowed 와 safetyTxBlocked 를 같이 볼 것. latActive=true 인데 controlsAllowed=false 면 panda safety 의심.
  4. 시동 꺼진 책상 위 harness 값은 주행 문제의 증거가 아님.
  5. 커밋/푸시는 개인 fork(abraxas4/*)만. upstream에 push하지 않음. 이번 수정은 새 모듈 fork 없이 opendbc fork만으로 충분.
