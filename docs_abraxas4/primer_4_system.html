CPU vs GPU

CPU vs GPU

두 프로세서의 근본적인 차이는 "코어 수"와 "코어 성능"의 트레이드오프입니다.

CPU

코어 수: 4~16개
코어 1개 성능: 매우 높음
순차적 복잡한 로직에 강함
분기/조건문 처리 뛰어남

ATM 제어기: 순서대로 카드 읽고, 금액 확인하고, 출금하는 복잡한 로직

GPU

코어 수: 수백~수천 개
코어 1개 성능: 낮음
같은 연산을 병렬로 처리에 강함
이미지/행렬 연산 뛰어남

128×256 이미지의 모든 픽셀에 동일 연산을 동시 수행

openpilot 적용:
Conv2D 연산 = 이미지의 모든 위치에 같은 필터 곱셈 → GPU에 완벽히 적합.
Adreno 630 GPU가 동시에 수천 픽셀을 처리해 20ms 안에 완료합니다.

OpenCL

OpenCL Open Computing Language

GPU를 범용 계산에 사용하기 위한 표준 API입니다. 다양한 GPU 제조사(Intel, AMD, Qualcomm 등)에서 동작하는 코드를 작성할 수 있습니다.

  // OpenCL 커널 예시 (GPU에서 실행되는 함수):
  __kernel void add_arrays(__global float* a,
                           __global float* b,
                           __global float* c) {
      int id = get_global_id(0);  // 몇 번째 코어인지
      c[id] = a[id] + b[id];      // 각 코어가 자기 담당 요소만 처리
  }
  // 1024개 요소 → 1024개 GPU 코어가 동시에 1개씩 처리
openpilot 적용: tinygrad가 신경망 연산(Conv2D, MatMul 등)을
OpenCL 커널로 변환해 Adreno 630에 실행합니다.

ISA — 명령어 집합 구조

ISA Instruction Set Architecture

프로세서가 이해하는 기계어 명령어 집합입니다. CPU마다 다릅니다.

  CPU ISA 예시:
  ARM     → ARM Thumb2 (임베디드 MCU)
  x86_64  → Intel/AMD PC
  Aarch64 → 스마트폰 CPU (comma 3x의 CPU)

  GPU ISA 예시:
  IR3     → Qualcomm Adreno (comma 3x의 GPU)
  PTX     → NVIDIA GPU
  GCN     → AMD GPU
openpilot 적용:
tinygrad의 IR3Renderer가 신경망 연산 → Adreno IR3 어셈블리로 변환.
이 과정을 "컴파일"이라고 합니다.

JIT 컴파일

JIT Just-In-Time Compilation

프로그램 실행 중에 코드를 컴파일하는 방식입니다. 처음 한 번은 느리지만, 이후 실행은 미리 최적화된 코드를 사용합니다.

  AOT (Ahead-of-Time, 임베디드 펌웨어 방식):
  소스코드 ──▶ [빌드 PC에서 컴파일] ──▶ .bin 플래싱 ──▶ 실행

  JIT (tinygrad 방식):
  ONNX 파일 ──▶ [첫 실행 시 GPU 코드 생성] ──▶ .pkl 저장 ──▶ 이후 빠른 실행
                       ↑
               Adreno 630에 맞는 최적화 코드 자동 생성
openpilot 적용:
driving_tinygrad.pkl = JIT 컴파일 결과물.
처음 모델 설치 시 컴파일(수 분 소요), 이후 재시동에서는 pkl을 바로 로드.
openpilot 업데이트 후 첫 실행이 느린 이유입니다.

IOCTL

IOCTL Input/Output Control

리눅스에서 디바이스 드라이버에 특수 명령을 보내는 시스템 콜입니다. 임베디드에서 레지스터 직접 쓰기와 유사합니다.

  // C 비유 — MCU 레지스터 직접 제어:
  *((volatile uint32_t*)0x40021000) = 0x01;  // GPIO 레지스터 쓰기

  // Linux GPU IOCTL:
  ioctl(gpu_fd, KGSL_IOCTL_DRAWCTXT_CREATE, &param);
  // GPU 드라이버에 "컨텍스트 만들어" 명령 전송

  // KGSL = Kernel Graphics Support Library (Qualcomm GPU 드라이버)
openpilot 적용: tinygrad의 ops_qcom.py가
KGSL IOCTL을 통해 Adreno 630에 GPU 작업을 제출합니다.

Command Buffer / Cache Flush / Memory Barrier

Command Buffer — 명령 버퍼

GPU에 보낼 연산 명령들을 미리 메모리에 패킹해두는 것입니다. DMA처럼 CPU 개입 없이 GPU가 직접 읽어 실행합니다.

  // 임베디드 비유 — DMA descriptor:
  DMA_DESC desc[] = {
      {src=camera_buf, dst=gpu_mem, len=1920*1088},
      {src=weights,    dst=gpu_mem, len=50*1024*1024},
  };
  DMA_start(desc);  // CPU는 다른 일, DMA가 알아서 처리

  // GPU Command Buffer (PKT7/PKT4):
  buffer[] = {PKT7_header, compute_dispatch_cmd, ...}
  ioctl(KGSL_IOCTL_SUBMIT_COMMANDS, buffer);
Cache Flush / Memory Barrier

CPU와 GPU가 같은 메모리를 공유할 때 캐시 불일치를 방지합니다. 임베디드에서 __DSB(), __ISB()와 동일한 개념입니다.

  // MCU에서:
  write_sensor_data(buf);
  __DSB();          // 데이터가 실제로 메모리에 쓰였음을 보장
  DMA_start(buf);   // 그 다음 DMA 시작

  // GPU에서:
  write_input_tensor(gpu_mem);
  cache_flush(gpu_mem);    // GPU가 최신 데이터를 봄을 보장
  submit_gpu_kernel();

Zero-copy / Rolling Buffer

Zero-copy — 복사 없음

데이터를 복사하지 않고 포인터만 전달하는 기법입니다. 임베디드에서 memcpy 대신 포인터를 넘기는 것과 같습니다.

  // 일반 방식 (복사 있음):
  uint8_t local_buf[1920*1088];
  memcpy(local_buf, camera_buf, sizeof(local_buf));
  process(local_buf);  // 1.5MB 복사 발생 → 느림

  // Zero-copy:
  process(camera_buf);  // 원본 주소 직접 전달 → 빠름
openpilot 적용:
Tensor.from_blob(ptr, shape) — 카메라 버퍼 주소로 직접 GPU 텐서 생성.
1920×1088 = 약 3MB를 복사하지 않아도 됨 → 20Hz 실시간 처리 가능.
Rolling Buffer — 순환 버퍼

새 데이터가 오면 가장 오래된 데이터를 밀어내는 FIFO 구조입니다. 임베디드의 링 버퍼(Ring Buffer)와 동일합니다.

  // 임베디드 링 버퍼:
  uint8_t ring[8];
  int head = 0, tail = 0;
  void push(uint8_t v) { ring[head++ % 8] = v; }

  // tinygrad features_buffer (24프레임 유지):
  # 새 프레임 들어오면 맨 앞 프레임 제거
  feat_q = feat_q[1:].cat(new_feat, dim=0)
  # → (24, 512) 유지하며 최신 24프레임 기억

Cereal / pub-sub / IPC

IPC Inter-Process Communication

서로 다른 프로세스가 데이터를 주고받는 방법입니다. openpilot은 여러 프로세스(modeld, controlsd, calibrationd 등)가 동시에 실행되며 메시지로 통신합니다.

  [modeld]           [controlsd]         [selfdrived]
  신경망 실행  ──▶   조향 계산    ──▶   engage/disengage
      │                  ↑
      │     modelV2      │  carState
      └──────────────────┘

  각 프로세스는 독립적으로 실행되며, 메시지(cereal)로 데이터 공유
Pub-Sub 패턴 Publish-Subscribe

발행자(Publisher)가 메시지를 토픽에 올리면, 구독자(Subscriber)가 읽어가는 패턴입니다. CAN 버스의 broadcast와 유사합니다.

  // CAN 버스 비유:
  // ID=0x3B6 메시지를 버스에 올리면 관심 있는 ECU가 수신

  // openpilot cereal:
  // modeld가 'modelV2' 메시지 발행
  pm = PubMaster(['modelV2'])
  pm.send('modelV2', msg)   // Publish

  // controlsd가 구독
  sm = SubMaster(['modelV2', 'carState'])
  sm.update()
  model = sm['modelV2']     // Subscribe
Cereal — openpilot 메시지 직렬화 라이브러리

openpilot에서 사용하는 메시지 포맷/전송 시스템입니다. Cap'n Proto 기반으로 이진 직렬화하여 빠릅니다.

  // 메시지 타입 정의 (log.capnp):
  struct ModelV2 {
    position   @0 :XYZTData;    // 경로 위치
    laneLines  @1 :List(XYZTData);  // 차선
    leadOne    @2 :Lead;        // 앞차
  }

  // 생성:
  msg = messaging.new_message('modelV2')
  msg.modelV2.position.x = [1.0, 2.0, ...]
  pm.send('modelV2', msg)
주요 메시지 토픽:
modelV2 — 신경망 출력 (차선, 앞차, 경로)
carState — 차량 상태 (속도, 조향각, TPMS)
controlsState — 제어 상태 (PID 값)
selfdriveState — engage/disengage, experimental mode
liveCalibration — 카메라 보정값 (rpyCalib)
liveParameters — 학습된 차량 파라미터 (steerRatio 등)

Pickle 포맷

Pickle — Python 직렬화

Python 객체를 파일로 저장하는 포맷입니다. 임베디드의 NVM 저장과 유사하나, Python 객체 전체를 저장합니다.

  // C 임베디드 비유 — NVM에 구조체 저장:
  NVRAM_write(&calib_data, sizeof(CalibData));
  NVRAM_read(&calib_data, sizeof(CalibData));

  // Python pickle:
  import pickle
  pickle.dump(jit_model, open('driving_tinygrad.pkl', 'wb'))  # 저장
  jit_model = pickle.load(open('driving_tinygrad.pkl', 'rb')) # 로드
openpilot 적용:
driving_tinygrad.pkl = JIT 컴파일된 신경망 실행 객체.
모델 파일 로드 후 바로 GPU 실행 가능. (재컴파일 불필요)

전체 연결 관계 정리

  카메라 DMA 버퍼  (NV12, uint8, 1920×1088)
         │  zero-copy (포인터만 전달)
         ▼
  Warp Stage (OpenCL → Adreno 630 GPU)
  · NV12 → YUV 분리 (deinterleave)
  · Perspective Transform (3×3 행렬 × 픽셀좌표)
  · 출력: img_q Tensor (float32, 1×12×128×256)
         │
         ▼
  Policy Stage (JIT 컴파일 커널 → Adreno 630)
  · Conv2D × N (이미지 특징 추출)
  · BatchNorm + ReLU (정규화 + 활성화)
  · LSTM (hidden_state로 시간 기억)
  · MDN 헤드 (다중 가설 출력)
         │
         ▼
  parse_model_outputs.py
  · sigmoid → 확률 (0~1)
  · softmax → 분포 (합=1)
  · MDN → mean + std 분리
         │
         ▼
  Cereal 메시지 발행 (modelV2 토픽)
  · controlsd가 구독 → CAN 명령 → 차량 제어
