1. 공식 목표 (꼭 읽을 것)

한 문장 목표

openpilot driving model 과 같은 입·출력 꼴(interface / shape) 을 가진 우리 아기 model 을 PC 에서 학습·export 하고, 나중에는 3X openpilot 의 model 자리에 replace 했을 때 프로세스가 에러 없이 돌아가는 것을 목표로 한다. comma 수준의 운전 기능을 따라가는 것은 목표가 아니다.

interface / shape (인터페이스 · 꼴)

“플러그에 핀이 몇 개이고, 각 핀이 어떤 이름·크기(tensor shape)의 숫자를 받거나 내는지”를 말합니다. 기능이 어른 수준인지는 별개입니다. USB-C 모양만 같으면 꽂히지만, 안쪽 칩 성능은 천차만별인 것과 비슷합니다.

replace (교체)

openpilot 이 기본으로 쓰는 driving model 파일(또는 그에 해당하는 산출물) 대신 우리가 만든 model 을 넣어 modeld 등이 그대로 읽게 하는 것입니다. 이 문서의 성공 기준은 “도로를 사람처럼 달린다”가 아니라 “꼴이 맞아 파이프라인이 기동·추론 루프를 돈다” 입니다.

1.1 어른 model vs 아기 model

comma / openpilot (어른) 우리 lab 목표 (아기)
입·출력 핀 배치 공식 supercombo 스펙 동일하게 맞춤
weights 의미·운전 품질 대규모 데이터로 학습됨 약함·단순함 OK (“아기”)
성공 기준 실제 주행 성능 replace 후 파이프가 돈다
comma 공식 weights 를 이어서 update comma 인프라 목표 아님 — 우리 weights 를 새로 만듦
그림 M1. 목표는 기능 복제가 아니라 같은 소켓에 아기 model 을 꽂는 것

1.2 목표에 포함 / 미포함

포함 (한다) 미포함 (지금은 안 함 · 성공 조건 아님)
입·출력 shape · 이름 · slice 를 openpilot 과 맞춤 comma 급 차선·신호·추종 성능
PC 에서 dataset · train · export (ONNX 등) comma 공식 weights 파일을 “이어서” fine-tune 하는 비법 재현
자동 label (사람 검수 생략 가능) · 전체 batch 학습 도로에서 아기로 안전 완전자율 주행
replace 후 modeld / 메시지 루프가 깨지지 않음 (우선 replay·안전한 환경) “잘 달린다”는 체감 품질
3X 는 openpilot_mj_develop git 그대로 유지 3X 위에서 training
안전 한 줄

아기 model 은 숫자를 내더라도 운전 의미는 거의 없을 수 있습니다. replace 실험은 가능하면 PC replay 또는 바퀴가 뜨거나 통제된 환경에서 먼저 하고, 일반 도로에서 “아기”로 engage 하는 것은 이 문서의 목표가 아닙니다.

2. 꼭 필요한 단어

아래에서 나오는 영어 단어는 처음 나올 때 뜻을 붙입니다. computer science 단어는 영어 그대로 둡니다.

open source

소스 코드를 공개하고, 라이선스 조건 아래 읽고 수정할 수 있는 소프트웨어입니다. 이 lab 의 Python 코드와 openpilot 의 host code 가 여기에 해당합니다.

e2e (end-to-end)

중간 단계를 사람이 많이 나누지 않고, 모델이 input 에서 control 에 가까운 output 을 바로 내도록 한 방식입니다. 예: 이미지 → 가속 숫자.

training (learning)

데이터를 보고 model 안의 weights 를 업데이트하는 과정입니다. “학습”이라고 부릅니다. 초보 lab 은 보통 입력과 목표 값(label) 짝으로 합니다. label 은 사람 손일 수도, 차 로그 자동일 수도 있습니다. GPU 가 있으면 더 빠르지만, 이 lab 은 CPU 만으로도 돌아갑니다.

inference

이미 정해진 weights 로 새 input 을 넣어 output 을 계산하는 실행입니다. training 과 달리 weights 를 바꾸지 않습니다. 차가 달릴 때 modeld 가 하는 일이 inference 입니다.

weights

model 내부의 숫자 파라미터입니다. training 이 이 숫자를 바꾸고, inference 는 이 숫자를 고정한 채 계산합니다. 파일로는 .pt, .onnx 등에 저장됩니다.

black box

input 과 output 은 보이지만, 내부에서 “왜 그 값이 나왔는지”를 사람이 쉽게 설명하기 어려운 부분을 말합니다. neural network 의 weights forward 가 대표적입니다. open source 여도 이 구간은 해석이 어렵습니다.

pipeline

데이터가 여러 단계를 순서대로 지나는 처리 사슬입니다. 예: image → preprocess → model → postprocess → log.

3. learning · label · 사람 수정

초보 때 많이 듣는 말이 “label 이 있는 학습 / 없는 학습” 입니다. 여기서 label = 사람이 매번 손으로 개입한다 와 같다고 생각하면 오해가 생깁니다.

label (다시, 아주 쉽게)

model 이 “이 입력에 대해 맞춰야 할 목표 값”입니다. 사진 옆의 정답 숫자, 정답 클래스 이름, “다음 1초 뒤 차 위치” 같은 것이 모두 label 이 될 수 있습니다. 누가 만들었는지와는 별개입니다.

3.1 초보용 큰 그림 2가지 (+ 한 가지 더)

방식 한 줄 label? 사람이 매번 클릭?
supervised learning
(지도 학습)		 입력 X 와 목표 Y 를 짝으로 주고, Y 를 맞추게 한다 있음 (Y) 꼭 아님. Y 는 센서·로그가 자동 생성 가능
unsupervised learning
(비지도 학습)		 정답 Y 없이 데이터 패턴만 본다 (군집, 압축 등) 없음 보통 없음. 대신 “가속 몇 m/s²” 같은 운전 숫자는 바로 안 나옴
self-supervised
(자기 지도, 초보 메모)		 데이터 안에서 가짜 문제를 만들어 스스로 정답을 만듦
(예: 다음 frame 맞히기)		 겉보기엔 없음, 안에서는 자동 생성 사람 클릭 거의 없음. 구현·해석이 더 어려움
supervised learning

“이 그림 → 이 숫자(또는 이 클래스)”처럼 짝을 주고 오차(loss)를 줄이는 학습입니다. 이 lab 의 train.py 가 supervised 입니다.

unsupervised learning

정답 짝 없이 데이터 구조만 찾는 학습입니다. 예: 비슷한 장면끼리 묶기. 초보 lab 의 “desired_accel 맞추기” 목표와는 잘 안 맞습니다.

그림 L1. supervised 라도 label 출처는 A/B/C 세 갈래. “사람 개입만”이 아님
질문: “label 은 사람이 개입하는 방식이죠?”

반만 맞습니다. label 이 있다는 것 = supervised 쪽이라는 뜻에 가깝습니다. 그런데 그 label 을 사람이 마우스로 다는 경우도 있고, 차가 이미 기록한 숫자(속도, 가속도, 조향)를 label 로 쓰는 경우도 있습니다. 후자는 매일 운전만 해도 데이터가 쌓입니다. frame 마다 클릭할 필요가 없습니다.

imitation learning / behavioral cloning (흉내 학습)

사람이(또는 다른 정책이) 실제로 한 행동을 label 로 두고, 같은 상황에서 비슷하게 행동하도록 배우는 방식입니다. supervised 의 한 형태입니다. “그때 운전자가 감속했으니, 그 장면 → 음수 accel” 이 전형적인 예입니다.

3.2 “label 없이” 우리는 할 수 없나?

하고 싶은 것 label 없이? 초보 추천
pipeline 연습 (지금 lab) synthetic 이 자동 label 제공 지금 바로
실차 영상으로 “가속 비슷한 숫자” 맞추기 순수 영상만으로는 매우 어려움 영상 + 로그에서 자동 label
순수 unsupervised 만 가능은 함 (패턴 묶기 등) 운전 control 숫자와 연결이 약함. 나중 숙제
self-supervised (다음 frame 예측 등) 사람 label 거의 없이 가능 코드·이론 부담 큼. 1단계는 아님

정리: “사람 손 label 없이” 는 가능하고 권장에 가깝습니다. “아무 목표 값도 없이” 운전용 숫자를 배우기는 초보 단계에서 비추천입니다. 차 로그가 있으면 그게 곧 자동 label 입니다.

3.3 합의된 작업 방식 (현재)

사람 검수 없이 전 자동
  1. 로그로 자동 label 생성 (vEgo 미분 등)
  2. 정지 frame 만 보고 가속/감속 고치기는 하지 않음 (비현실적)
  3. 있는 qcamera+qlog segment 를 batch 전체 처리 후 train
  4. (선택) 나중에 이상치·그래프 검수가 필요하면 그때 추가

2026-08-10 기준: batch_process_all 444 segs · 52k samples · train_real → artifacts/real_auto_accel.pt 완료. 상세 수치는 e2e_learning_progress_log_byGrok.html 참고.

4. dataset 이란? “dataset 만들기”는 뭔가?

초보자가 가장 자주 하는 질문입니다. “dataset 만들기”가 대체 뭐 하는 단계인가요? (위 3절의 label 개념을 먼저 읽으면 더 쉽습니다.)

dataset

model 을 가르치거나 시험할 때 쓰는 예제 모음입니다. 학교 시험 문제집과 비슷합니다. 각 문제는 “입력(문제)”과 “정답(label)”이 짝으로 있습니다.

sample (샘플 / 한 줄 예제)

dataset 안의 한 개 예제입니다. 이 lab 에서는 보통 이미지 1장 + 숫자 정답 1개 가 한 sample 입니다.

label (정답 / 목표 값)

그 sample 에 대해 “모델이 맞춰야 할 답”입니다. 이 lab 에서는 desired_accel 같은 숫자입니다. 사람만 만드는 것이 아닙니다. 프로그램·차 센서 로그가 만들 수 있습니다. 사진만 있고 목표 값이 전혀 없으면, supervised 로 “accel 숫자”를 가르치기 어렵습니다.

supervised learning

“문제 + 정답” 쌍으로 weights 를 업데이트하는 학습 방식입니다. 이 lab 의 train.py 가 여기에 해당합니다. (정답 없이 패턴만 찾는 방식은 unsupervised 등으로 부릅니다. 지금은 몰라도 됩니다.)

4.1 비유로 한 번 더

학교 이 lab
문제집 전체 dataset
문제 한 문항 한 sample (이미지 파일 하나)
문제 지문 input (카메라 프레임 / png)
정답지 label (labels.csv 의 숫자)
문제집 인쇄·제본 dataset 만들기 (make_dataset)
학생이 문제 풀며 공부 training
새 문제로 실력 확인 inference / validation

그래서 python -m src.make_dataset 은 “신경망을 돌린다”가 아니라, 공부용 문제집 파일을 디스크에 만들어 두는 준비 단계입니다. training 전에 한 번(또는 데이터가 바뀔 때마다) 실행합니다.

그림 A. dataset 만들기 → training → inference 순서

4.2 lab 이 실제로 만드는 파일

python -m src.make_dataset 실행 후 대략 이런 구조가 생깁니다.

data/

    img_0000.png

파일 역할
img_XXXX.png input. model 이 “보는” 그림
labels.csv 각 그림의 정답 숫자 표
train/ 공부용 (weights 를 바꿀 때 사용)

train split / val split

dataset 을 나누는 묶음입니다. train 으로 배우고, val 로 “처음 보는 것 비슷한 그림”에서 점수를 봅니다. 같은 그림으로만 공부하고 같은 그림으로 시험하면, 외웠는지 실력이 있는지 구분이 안 됩니다.

synthetic dataset

실제 도로를 찍지 않고, 프로그램이 규칙을 정해 가짜로 만든 dataset 입니다. lab 기본 make_dataset 은 synthetic 입니다. 장점: 인터넷·장치 없이 바로 training 연습. 단점: 진짜 도로 운전 실력과는 거리가 큼.

4.3 지금 lab 의 synthetic 규칙은 뭔가?

진짜 신호등을 읽는 것이 아닙니다. 오직 pipeline 연습용입니다.

  • 그림 안에 빨간 덩어리가 많으면 → label 을 음수 쪽에 (감속 느낌)
  • 초록 덩어리가 많으면 → label 을 양수 쪽에 (가속 느낌)

model 은 “이 규칙”을 숫자 weights 로 비슷하게 맞추는 법을 배웁니다. 나중에 실차 영상으로 바꾸면, 같은 training 코드에 다른 문제집을 넣는 것입니다.

초보가 자주 하는 오해
  • “dataset 만들기 = AI 학습” → 아니오. 문제집 준비일 뿐입니다.
  • “이미지만 있으면 학습된다” → supervised 에서는 label 도 필요합니다.
  • “한 번 make_dataset 하면 끝” → 규칙을 바꾸거나 실차 영상으로 바꾸면 다시 만듭니다.

5. comma 학습 vs 우리 학습

공개 자료와 커뮤니티 설명 기준으로, 초보에게 필요한 수준만 말합니다. (comma 내부 학습 스택 전체가 이 monorepo 에 다 있는 것은 아닙니다.)

한 줄

comma 의 driving model 학습은 “완전 랜덤 무정답 방치”가 아닙니다. 대규모 실차 주행 로그를 쓰며, 그 안에 이미 들어 있는 미래 궤적·실제 움직임·(과제에 따라) 사람 주석 등을 목표(supervision) 로 삼는 쪽에 가깝습니다. 즉 “label 이 전혀 없다”기보다, 사람이 frame 마다 빨간불을 클릭하지 않아도 로그가 supervision 을 제공한다에 가깝습니다.

종류 comma 쪽에서 보이는 예 사람 손?
실차 로그 supervision 주행 중 카메라 + 차 상태 + 시간이 같이 기록됨. “그 다음 순간 차가 어떻게 움직였는지”를 목표로 쓸 수 있음. Wi‑Fi 로 데이터가 모이면 더 나은 model 학습에 쓰인다고 안내함. 운전은 하지만, frame 주석 클릭은 아님
별도 주석 dataset 예: comma10k — 이미지에 사람이 영역 등을 달아 개선에 기여할 수 있음 있는 경우 (특정 과제)
이 lab 기본 synthetic 그림 + 프로그램이 만든 숫자 없음 (자동)
이 lab + 매일 10 km 영상 + (권장) qlog/rlog 에서 속도·가속 추정 운전만, 클릭 label 불필요
supervision (지도 신호)

training 때 “이 방향이 맞다”고 알려 주는 정보입니다. supervised learning 의 label 이 곧 supervision 입니다. 출처는 사람·센서·합성 데이터 모두 가능합니다.

우리와 comma 의 스케일 차이
  • comma: 매우 많은 차량·시간·엔지니어링. 공식 supercombo 를 집에서 똑같이 재학습하기는 비현실적.
  • 우리: 같은 입출력 꼴의 아기 model 을 PC 에서 만들고, 로그 supervision 으로 연습.
  • comma 공식 weights 를 “이어서 update”하는 것이 목표가 아니라, 우리 weights 를 새로 만들어 소켓에 꽂는 것.

7. 입출력 “핀” — 개수만 알고 내용은 모르나?

답

아니오. open source 기준으로 어느 핀에 어떤 종류의 내용인지는 상당 부분 알 수 있습니다. 모르는 쪽은 그 숫자를 weights 가 어떻게 계산했는지(black box) 입니다.

핀 배치표 vs 칩 내부

커넥터 실크스크린(이름·핀 번호)은 회로도(open source)에 있고, 플라스틱 안의 ASIC 이 왜 그 전압을 내는지는 데이터시트에 없을 수 있습니다. openpilot model I/O 가 전자, weights forward 가 후자입니다.

7.1 입력 핀 (modeld 가 넣는 것, 개념)

핀(이름·개념) 내용 코드 힌트
road image / wide image 전방·광각 카메라 (warp 후 model 해상도) modeld.py VisionIPC
desire / desire_pulse 차로 변경 등 의도 (길이 8 근처) DESIRE_LEN, DesireHelper
traffic_convention 좌·우핸 (길이 2) LHD/RHD
action_t 횡·종 delay 시간 2개 actuator delay + frame delay
features_buffer / prev_feat 과거 feature (예: 24×512 계열) 이전 hidden 을 다시 넣음 — 칸 의미는 black box
warp matrix 캘리브 반영 변환 liveCalibration
tensor shape

각 핀의 숫자 배열 크기입니다. 예: (1, 12, 128, 256), (1, 2). 장치 위 실제 ONNX metadata 의 input_shapes 가 정본에 가깝고, 로컬 브랜치 compile_modeld.py 주석·constants 와 맞춰 확인합니다.

7.2 출력 핀 (파서가 자르는 것, 개념)

핀(이름) 내용 참고
plan 미래 위치·속도·가속도·자세 등 (33 시점 × PLAN_WIDTH 등) constants.Plan slice: POSITION, VELOCITY, ACCELERATION…
lane_lines / road_edges 차선·도로 가장자리 파서 MDN
lead 앞차 가설
action desired curvature / acceleration 쪽 (있으면) e2e 종방향과 연결
meta disengage, hard brake 확률 등 Meta slice
desire_state desire 확률
hidden_state 다음 step feature 의미 해석 어려움

이 출력들이 fill_model_msg 를 거쳐 modelV2 메시지 필드가 됩니다. “핀 번호표”의 정본에 가까운 곳: parse_model_outputs.py, constants.py, log.capnp 의 ModelDataV2, ONNX 의 output_slices metadata.

정리
  • 핀 개수·이름·종류 → open source 로 알 수 있음 (버전별 확인 필요)
  • 핀 값의 왜 → weights black box
  • 아기 model 목표는 그 번호표를 그대로 지키는 출력을 내는 네트워크를 우리 손으로 학습·export

8. 꼴 맞추기 replace (아기 model) — 목표의 핵심

“입출력 개수를 맞춰 러닝할 수 있나?” → 예, 그것이 이 프로젝트의 중심 목표입니다. 단, 개수만 맞추는 것이 아니라 이름·shape·slice·후처리가 기대하는 형식까지 맞춰야 replace 시 파이프가 돌아갑니다.

단계 의미 성공 느낌
A. 스펙 고정 현재 쓰는 openpilot model 의 input_shapes, output_slices 를 문서화 핀 번호표 완성
B. 아기 네트워크 같은 I/O 의 작은/단순 net (성능 무관) forward 가 shape 에러 없이 끝남
C. 학습 로그 자동 label (검수 생략 가능); 일부 head 는 dummy/teacher loss 가 돌아가기만 해도 1차 OK
D. export openpilot 이 읽는 형식(ONNX 등) + metadata modeld 로드 성공
E. replace 검증 우선 PC replay / 장치에서 modeld 기동 크래시 없이 modelV2 발행
dummy / teacher head

출력 핀은 모두 채워야 하는데, 초보가 모든 핀에 좋은 label 을 못 만들 수 있습니다. 일부 출력은 0·평균·기존 openpilot 출력(teacher)을 따라 가게 두고, 우리가 집중하는 핀(예: action 가속)만 실차 로그로 학습해도 “꼴 유지” 실험에는 도움이 됩니다.

replace ≠ 잘 달린다

아기 model 이 소켓에 꽂혀 modeld 가 돌아도, plan/차선/가속이 엉망일 수 있습니다. 그 상태에서의 도로 engage 는 위험합니다. 목표 달성은 “돌아간다”이지 “잘 간다”가 아닙니다.

지금 lab (TinyAccelNet) 과의 관계

TinyAccelNet 은 입력 1장·출력 1숫자. synthetic 연습 후, 실차 qcamera 전체 batch 로 real_auto_accel.pt 까지 학습 완료. 여전히 openpilot replace 꼴은 아님.

model 틀 vs weights: 틀(I/O·architecture)은 한 번 맞추고, 그 뒤 학습 사이클마다 weights 만 업데이트한다. “데이터 학습을 다 한 뒤 마지막에만 I/O 를 맞춘다”가 아니다.

lab venv 는 CUDA 빌드(torch 2.6+cu124, RTX 4050) 설치됨. 같은 dataset 으로 GPU train 가능. 다음 마일스톤: openpilot 동일 I/O 아기 net.

CPU, GPU, 메모리 컨트롤러 등을 한 칩에 모은 부품입니다. phone / 자동차 컴퓨터에 많이 씁니다. comma 장치는 SoC 위에서 AGNOS Linux 가 돕니다.

3X 가 PC 보다 “항상 더 강력하다”고 보면 안 됩니다. 3X 는 전력·발열·지연시간·차량 연동에 맞춘 장치입니다. 데스크톱에 NVIDIA GPU 가 있으면 training 은 거의 항상 PC 가 유리합니다. GPU 가 없어도 이 lab 규모(작은 CNN, 이미지 수백 장)는 노트북 CPU 로 충분합니다.

그림 1. learning lab 은 PC, 실차 openpilot 은 3X

10. 3X 실차 동영상 + 매일 10 km

짧은 답

예, 쓸 수 있고, 매일 10 km 를 쌓는 것도 좋은 계획입니다. (1) 영상·로그는 PC 로 가져오고, (2) training 은 PC 에서 하며, (3) 가능하면 로그에서 자동 label 을 만듭니다 (사람 클릭 불필요). 영상만 있고 로그가 전혀 없으면 supervised 로 “accel 숫자”를 가르치기 어렵습니다.

매일 10 km 를 어떻게 쓰면 좋은가
  1. 그날 route 를 장치에 남긴다 (평소 openpilot 기록).
  2. 집에 와서 Wi‑Fi/SSH 로 qcamera + qlog 정도만 PC 로 복사 (처음엔 segment 일부만).
  3. PC 에서 frame 추출 + 로그 시각 맞춰 labels.csv 자동 생성 (스크립트는 단계적으로 추가).
  4. train/ 에 날짜별로 쌓고, 가끔 val 은 다른 날로 둔다.
  5. PC 에서 짧게 train → loss 가 내려가는지만 본다. 실차 제어 연결은 하지 않는다.

사람 label 작업(마우스로 신호등 표시)은 필수가 아닙니다. 운전자가 달린 것 자체가 imitation 용 supervision 이 됩니다.

route / segment

openpilot 은 시동 ON~OFF 한 번을 route 로 묶고, 약 1분 단위 segment 폴더로 저장합니다. 장치 경로 예: /data/media/0/realdata/0000022d--75541d0fce--5/

10.1 장치에 있는 동영상 종류

SSH 예: ssh -i ~/.ssh/openpilot_ed25519 comma@192.168.35.191 (사용자 환경 기준).

파일 내용 learning 에
fcamera.hevc 전방 카메라, H.265, 고해상·용량 큼 (세그먼트당 수십 MB) 품질 좋음. PC 로 복사 후 frame 추출

동영상 압축 방식입니다. .hevc 는 H.265 로 많이 저장되고, qcamera.ts 는 H.264 쪽입니다. PC 에서 ffmpeg 등으로 풀 수 있습니다.

10.2 왜 “영상만”으로는 부족한가

그림 B. 실차 learning 에는 영상 + label 이 한 세트

label 을 만드는 현실적인 방법 (초보 추천 순):

  1. 로그에서 자동 (추천) — 같은 시각의 carState.vEgo 변화를 보고 대략 accel 을 계산해 label 로 씀. 매일 10 km 운전 = 자동으로 문제집 원재료가 늘어남. 사람 클릭 불필요.
  2. 이미 있는 openpilot model 출력 — rlog 의 desiredAcceleration 등을 teacher label 로 쓰는 연습.
  3. 사람이 달기 — “이 프레임은 정지” 등. 느리므로 필수 아님. 특수 연구용.
teacher / student (초보 메모)

이미 잘 하는 model(teacher) 의 출력을 정답처럼 두고, 작은 model(student) 이 따라 배우게 할 수 있습니다. 이것도 supervised 이고, 사람 손 label 이 아닙니다.

이 PC 에는 이미 3X realdata 전체 복사본이 있을 수 있습니다 (예: e2e_learning_lab\data\from_3x\realdata, 약 66 GB). 이후에는 매일 증가분만 scp 하면 됩니다.

12. black box 는 어디인가

구간 lab 파일 성격
dataset 만들기 src/make_dataset.py open source
preprocess src/preprocess.py open source
model 구조 정의 src/model.py (레이어 목록) 구조는 읽힘

그림 3. black box 시작 = network 에 tensor 가 들어간 뒤, 끝 = raw output 숫자
forward (forward pass)

고정 weights 로 input tensor 를 레이어 순서대로 통과시켜 output 을 얻는 계산 한 번입니다. training 때는 여기에 더해 backward 로 weights 를 업데이트합니다.

tensor

다차원 숫자 배열입니다. 이미지는 보통 (batch, channel, height, width) 형태입니다.

epoch

training 에서 전체 training dataset 을 한 번 다 보는 단위입니다. lab 기본값은 여러 epoch 을 돕니다. 한 epoch 마다 train/val loss 를 출력합니다.

label

정답 이름표입니다. lab 에서는 desired_accel 숫자입니다. openpilot 실차 inference 로그에는 “빨간불” label 이 보통 없습니다.

loss

예측과 정답이 얼마나 다른지 나타내는 숫자입니다. lab 은 MSE (평균 제곱 오차) 를 씁니다. 작을수록 training 이 정답에 가깝게 맞추고 있다는 뜻입니다.

modeld

openpilot 에서 driving model inference 를 담당하는 process 입니다. 코드: openpilot/selfdrive/modeld/modeld.py.

Experimental Mode

openpilot 에서 model 의 e2e 가속 출력을 종방향 제어에 더 쓰는 모드입니다. lab 의 “accel 숫자를 믿는다”와 개념적으로 비슷하지만, 실차는 MPC 등과 섞고 safety 가 있습니다.

openpilot inference input (개념)

  • 전방 (및 wide) camera image
  • desire (차로 변경 의도 등)
  • traffic convention (좌/우핸)
  • action delay 시간
  • 이전 feature buffer

여기에 “traffic_light=red” 나 “speed_limit=50” 같은 label 은 기본 input 이 아닙니다.

openpilot inference output (개념)

  • plan 궤적, lane, lead, meta 확률 등
  • action: desired acceleration / curvature 쪽
  • shouldStop 일부는 open source 규칙으로 계산
