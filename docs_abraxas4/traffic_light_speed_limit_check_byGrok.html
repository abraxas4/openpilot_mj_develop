1. 한 줄 결론

부분 예 신호등

로그에 “빨간불/초록불” 같은 명시적 라벨은 없습니다. 대신 Experimental Mode에서는 신경망이 화면 전체를 보고 desiredAcceleration(원하는 가속)과 shouldStop(멈춰야 함)을 내보냅니다. 이번 16.8 km 주행에서 e2e(종단간) 감속·정차 신호가 활발히 동작했습니다. 따라서 “장면을 보고 멈추려는 행동”은 확인되지만, “신호등 객체를 따로 인식했다”고 로그로 증명할 수는 없습니다.

아니오 제한속도 (표지/지도)

이번 로그에는 지도/내비 기반 제한속도 메시지 (liveMapData, navInstruction.speedLimit)가 한 건도 없었습니다. 크루즈 설정 속도 vCruise는 전 구간 105 km/h로 고정되어 있었고, 이는 “표지판을 읽은 값”이 아니라 운전자(또는 시스템)가 잡은 크루즈 목표 속도입니다.

초보자를 위한 한 문장

이 차는 “신호등 글자를 로그에 적어두지는 않지만”, Experimental Mode에서는 AI가 영상만 보고 스스로 감속·정차 명령을 만들고 있었습니다. 반면 “이 도로는 50 km/h” 같은 제한속도 숫자는 로그에 나타나지 않았습니다.

2. 무엇을 확인했나

사용자 요청은 단순합니다. comma 3X에서 Experimental Mode로 달린 최근 주행 중, 특히 약 10 km 이상 구간에서 신호등과 제한속도를 인식하고 있는지 로그로 확인하라는 것입니다.

여기서 “인식”을 두 층으로 나눠 생각하면 오해가 줄어듭니다.

층 의미 로그에서 보이는 것
명시적 인식 “빨간불”, “제한 50 km/h”처럼 이름 붙은 결과 별도 메시지 필드 (예: 지도 속도, 내비 속도)
암시적 인식 (행동) 표지/신호의 이름을 안 써도, 감속·정차로 반응 desiredAcceleration, shouldStop, 종방향 계획 소스

stock openpilot(공식 구조)의 Experimental Mode는 주로 암시적 인식 쪽입니다. 신호등 전용 디텍터 출력을 로그에 남기지 않고, 운전 신경망이 바로 “얼마나 가속/감속할지”를 뱉습니다.

3. 어떤 주행 로그를 골랐나

장치 comma-e0ee42a4 (IP 192.168.35.191)에 SSH로 접속해 /data/media/0/realdata 아래 route 목록을 확인했습니다.

Route (라우트)

openpilot이 “시동(이그니션)이 켜진 뒤부터 꺼질 때까지” 한 번의 주행을 묶은 단위입니다. 이름은 보통 0000022b--6947e9c3c5처럼 순번--해시 형태입니다. 한 route는 다시 약 1분 단위의 segment(세그먼트)로 잘립니다.

4. openpilot은 신호등/제한속도를 어떻게 “보나”

Experimental Mode (실험 모드)

openpilot UI에서 켤 수 있는 종방향(가속/감속) 모드입니다. 켜면 전통적인 “앞차 거리 + 크루즈 속도” 중심 계획 위에, 카메라 신경망의 e2e(end-to-end, 종단간) 가속 명령이 더해집니다. 빨간불·횡단보도·정체 같은 장면에 더 잘 반응하도록 설계된 실험적 경로입니다.

e2e / End-to-End (종단간)

“차선 검출 → 신호등 분류 → 규칙으로 브레이크”처럼 단계를 나누지 않고, 카메라 이미지에서 바로 “가속값/정지 여부”를 신경망이 한 번에 예측하는 방식입니다. 장점은 장면 전체 맥락을 쓰기 쉽고, 단점은 로그에 “빨간불을 봤다”는 중간 증거가 잘 안 남는 것입니다.

이번 코드베이스(longitudinal_planner.py)의 핵심 분기는 아래와 같습니다. 

modelV2.action.desiredAcceleration   # 신경망이 원하는 가속 (m/s²)
modelV2.action.shouldStop            # 신경망이 “멈춰라”고 함

if experimentalMode:
    a_target = min(e2e_accel, mpc_accel)   # 둘 중 더 보수적(작은) 가속
    shouldStop = e2e_shouldStop OR mpc_shouldStop
else:
    a_target = mpc_accel                   # 전통 MPC만 사용
그림 1. Experimental Mode 종방향 제어 경로 (직선 화살표만 사용)

정리하면, 신호등을 “이름 붙여 분류”하지 않아도 신경망이 영상에서 감속 필요성을 배우면 desiredAcceleration < 0 또는 shouldStop = true로 나타납니다. 제한속도 표지판 역시 e2e가 암시적으로 반영할 수는 있지만, stock 경로에서는 보통 지도/내비 필드가 별도로 있어야 “숫자로 인식했다”고 말하기 쉽습니다.

5. 데이터가 흐르는 길 (파이프라인)

qlog / rlog

주행 중 프로세스들이 주고받은 메시지를 파일로 남긴 것입니다. rlog.zst는 거의 전부 기록(용량 큼), qlog.zst는 일부만 추려 담은 가벼운 버전입니다. 둘 다 zstd 압축과 Cap’n Proto 직렬화를 씁니다.

Cap’n Proto

메시지 스키마(필드 이름·타입)를 정해 두고, 프로세스 간/파일에 빠르게 읽고 쓰는 직렬화 포맷입니다. openpilot의 스키마는 openpilot/cereal/log.capnp에 있습니다.

중요한 해석 포인트

고속에서 신호등에 접근할 때 모델은 먼저 음의 가속도(감속)로 반응하고, 거의 멈춘 뒤에야 shouldStop=true로 “정지 유지”를 거는 패턴이 일반적입니다. 그래서 “shouldStop이 20 km/h 이상에서 0”이라고 해서 신호등 반응을 안 한 것은 아닙니다.

8. 신호등 인식 — 증거와 한계

그림 4. 신호등 관련 판단 구조

확인된 증거 (행동 수준)

  1. Experimental Mode가 전 구간 활성.
  2. drivingModelData.action이 지속 기록되고, 감속·정차 플래그가 대량 발생.
  3. longitudinalPlanSource = e2e가 주력 — 신경망 종방향이 실제로 선택됨.
  4. 거의 정지 시 shouldStop=true 비율이 매우 높음 → 정지선/정체/신호 대기와 양립.
  5. 중·저속에서 강한 감속 이벤트 존재 (앞차 또는 장면).

확인되지 않은 것 (라벨 수준)

  1. TrafficLight 상태 enum 메시지 없음 (deprecated trafficEvents도 이번 which 목록에 없음).
  2. 특정 시각의 shouldStop이 “빨간불 때문”인지 “앞차/정체 때문”인지 로그 단독 분리 불가.
  3. 영상 프레임과 1:1 대조는 이번 문서 범위에서 수행하지 않음 (장치에 fcamera.hevc는 존재).
실사용 관점

운전자 체감으로 “빨간불에 선다”와 로그의 “e2e가 감속·정지를 냈다”는 대체로 같은 파이프라인입니다. 다만 개발/검증 문서에서는 행동 증거와 클래스 라벨 증거를 구분해서 적는 것이 정확합니다.

10.2 Experimental 분기 (코드)

// openpilot/selfdrive/controls/lib/longitudinal_planner.py (요약)

output_a_target_e2e = sm['modelV2'].action.desiredAcceleration
output_should_stop_e2e = sm['modelV2'].action.shouldStop

if sm['selfdriveState'].experimentalMode:
    output_a_target = min(output_a_target_e2e, output_a_target_mpc)
    self.output_should_stop = output_should_stop_e2e or output_should_stop_mpc
    if output_a_target < output_a_target_mpc:
        self.mpc.source = LongitudinalPlanSource.e2e
else:
    output_a_target = output_a_target_mpc
    self.output_should_stop = output_should_stop_mpc
MPC (Model Predictive Control)

모델 예측 제어. 앞으로 몇 초의 속력 궤적을 수학적으로 최적화해 “지금 얼마로 가속할지”를 고르는 전통적 제어기입니다. openpilot에서는 앞차·크루즈 속도 제약을 넣은 종방향 MPC가 돌아가고, Experimental Mode에서는 이 결과와 신경망 e2e 가속 중 더 보수적인 쪽을 고릅니다.

10.3 왜 modelV2가 아니라 drivingModelData인가

services.py에서 modelV2의 qlog decimation은 None입니다. 로거 구현상 이는 qlog에 넣지 않는다는 뜻에 가깝습니다. 대신 drivingModelData(decimation 10)가 action을 포함하므로, qlog만으로도 e2e 가속/정지를 통계할 수 있습니다. 더 촘촘한 시계열이 필요하면 세그먼트의 rlog.zst를 읽으면 됩니다 (세그먼트당 약 8–9 MB, 이번 40–50분 주행은 수백 MB 규모).

10.4 which_seen에 없었던 것 (0000022b qlog)

  • modelV2 — 예상대로 qlog 미포함
  • liveMapData / liveMapDataDEPRECATED
  • navInstruction / navInstructionDEPRECATED
  • 구형 trafficEvents

즉 “제한속도 숫자 채널” 자체가 이 빌드·이 주행 설정에서는 동작/기록되지 않았습니다.

10.5 openpilot enabled 비율 참고

route 0000022b에서 selfdriveState.enabled=true는 3,961 / 23,364 샘플로, 전체 시간의 일부만 실제 제어 engage 상태였습니다. 그래도 모델 추론과 experimental 플래그는 계속 돌아가며 로그에 남습니다. “인식 파이프라인 동작 여부”와 “운전자가 핸즈온으로 engage 했는지”는 별개입니다.
